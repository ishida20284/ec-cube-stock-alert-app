# メンテナンスガイド

課題テンプレートを設計・改修するための設計メモ。**決定とその理由**を残す場所で、作業記録や、コードを読めば分かることは書かない。

この文書は `AGENTS.md` から意図的に分離してある。**戻さないこと**（理由は下記「ドキュメントの分担」）。

## 基本方針

- 自力で完了できるようにする
- 課題は作り込みすぎない
- 不足分は生成 AI によって埋めてもらう課題設計とする
- 最小限の課題とする

## ドキュメントの分担

`AGENTS.md`（`CLAUDE.md`）は**学習者のセッションでも毎回自動で読み込まれる**。この前提で3つに分けている。分担表は `AGENTS.md`「このリポジトリのドキュメントの分担」にあり、そちらが運用上の正。

| 置き場所 | 中身 | 読まれ方 |
| --- | --- | --- |
| `AGENTS.md` | 学習支援の方針（ヒント縛り・代筆禁止・コーディングスタイル） | 常時 |
| `.claude/skills/review/SKILL.md` | 受け入れ基準（境界値・エッジケースの期待挙動）とレビュー観点 | `/review` のときだけ |
| `docs/MAINTENANCE.md` | このファイル。テンプレート自体の設計メモ | メンテナが開いたときだけ |

分けた理由:

- **受け入れ基準が `REPORT.md`「動作確認の記録」の答え合わせ表になっていた。** 閾値 null・在庫==閾値・`stock_unlimited` などの期待挙動を伏せて学習者自身に確かめさせる設計なのに、常時読み込みの `AGENTS.md` に正解が並んでいると、「この実装で合ってますか」と聞かれた AI が突き合わせて答えを渡してしまう。方針で「答えるな」と書くより、**そもそも文脈に入れない**ほうが確実
- **メンテナンスガイドは学習者の AI が一度も使わない。** 常時読み込む意味がないうえ、コピペ対策の設計まで説明してしまう
- **スキルにしたのは「オンデマンドで読ませたい」から。** ただし**スキルにしても漏洩は防げない**（ファイルは学習者のリポジトリ内にあり、本人も AI も読める）。防げるのは自動読み込みによる事故だけで、意図的に読みに行くのは止められない。そこは割り切っている
- メンテナンスガイドをスキルにしなかったのは、スキルは名前と説明が毎セッションの一覧に載るため、**使わない資料の存在を宣伝してしまう**から。ただのファイルのほうが静か
- 配布物からも外すなら、Template Copy が既定でデフォルトブランチしか複製しないことを利用して別ブランチに置く手もあるが、ブランチが分岐して更新漏れが起きやすく「作り込みすぎない」方針と合わないため採らなかった

**スラッシュコマンドは Copilot と共有している。** 実体は `.github/prompts/<名前>.prompt.md` に置き、`.claude/commands/<名前>.md` から同名でシンボリックリンクする。README が「Copilot / Claude を使って」と書いている以上、どちらで叩いても同じ結果になる必要があるため。`.claude/commands/` 側だけを消すとリンクが切れて Copilot 側に古い実体が残るので、触るときは両方を見ること。

**プロンプトファイルからコマンドを実行させることはできない。** Claude Code でコマンド出力を埋め込む記法は frontmatter の `allowed-tools` と `` !`コマンド` `` の組み合わせで、Copilot のプロンプトファイルにはその仕組み自体が無い。共有している以上どちらでも動く書き方に限られるので、**「以下は実行結果です」と前置きせず、「このコマンドを実行してください」と指示する**こと。`check-env` は前者の書き方になっており、置換が起きずリテラルの `!bash scripts/check-env.sh` が AI に渡っていた。

`/review` だけは例外で、スキル（`.claude/skills/review/SKILL.md`）が実体、`.github/prompts/review.prompt.md` はそれを読ませるポインタになっている。スキルは frontmatter（`name` / `description`）を要求し、Copilot のプロンプトファイルと同一ファイルにできないため。シンボリックリンクで共有する案もあったが、Copilot がリンクを辿るか未確認で、失敗しても静かに壊れるだけなので、確実に動くポインタ方式を採った。

## マイグレーションの方針

EC-CUBE のスキーマ変更は2段構え。

| 変更内容 | 反映方法 |
| --- | --- |
| 単純なカラム追加・変更 | Entity にアノテーションを足すだけ。`doctrine:schema:update --force` が反映する。マイグレーション不要 |
| マスタ/初期データの INSERT、型変更・リネームなど `schema:update` で扱えない変更 | `app/DoctrineMigrations/`（namespace `DoctrineMigrations`）にマイグレーションを書き `doctrine:migrations:migrate` |

- **`doctrine:migrations:diff` は使わない**（EC-CUBE 公式方針）。単純なカラム差分まで ALTER として吐き出してしまい、上記の原則と矛盾するため。必要なときは `doctrine:migrations:generate` で空の雛形を作り、SQL を手で書く
- **本課題ではあえてマイグレーションを書かせる。** `stock_alert_threshold` は nullable・デフォルト値なしなので、技術的には `schema:update` で足りる。それでも書かせるのは、**カラム追加のたびにデフォルト値やデータ移行の要否を考える習慣**をつけさせるため。「スキーマの源泉は Entity」という EC-CUBE の設計思想自体は一般知識として README に残し、本課題は学習目的の例外、という体裁で説明している
- このリポジトリはインストーラーがスキーマを作るため、マイグレーションが一度も実行されていない。学習者が初めて `migrate` すると本体同梱の過去分（十数件）も一緒に走り、`was executed but did not result in any SQL statements` が大量に出る。実害はないので README に「無視してよい」と明記してある

## 規格切り替え時の追従を必須要件にした理由

フロントの商品詳細は Ajax を使わず、ページロード時に全規格分のデータを JSON として埋め込み、JS がそれを参照するだけの作り。そのため拡張ポイントは「`getClassCategoriesAsJson()` が返す配列に判定結果を1項目足す」「`checkStock()` に分岐を足す」の2箇所で済む。E2E 側も Ajax の完了待ちが不要で、セレクトを操作した直後に DOM を見れば検証できる。想定より簡単だったため必須要件とした。

## E2E テスト（Codeception）

**Codeception を採用**（EC-CUBE 本体と同じ）。全部 PHP で完結し、本体のテストコードをそのまま参考にできる。Playwright も比較したが、PHP バインディング（`playwright-php/playwright`）が非公式で実績が浅いため見送った。

- **Page Object パターン**を使い、`codeception/_support/Page/` の既存クラスを拡張する
- **テストメソッド名・操作名は日本語で書く**（本体の慣習）
- 対象は `@group stock_alert` を付けた `StockAlertAdminCest` / `StockAlertFrontCest` の2ファイルのみ。`ci.yml` もこのグループだけを実行し、本体の数百件の既存 Cest は動かさない
- **テストデータは管理画面の UI 操作で作る。** `Fixtures::get('entityManager')` で Doctrine を直接触るバックドア方式は使わない。UI で作れば「管理画面で閾値を保存できること」自体もテストになるため。バックドアは UI では作れないデータ（ダミーのマスタ等）向けの手段
- acceptance は WebDriver を要するため、`docker-compose.yaml` に `selenium/standalone-chrome` を `chrome` サービスとして置いている
- **Page Object のセレクタに位置指定（`div[2]` など）を使わない。** 学習者が検索フォームに項目を1つ足しただけで壊れ、「実装は正しいのにテストだけ落ちる」という最悪の失敗になる。`ProductManagePage::$詳細検索ボタン` が実際にこの状態だったため、開閉対象を指す属性（`[data-bs-toggle="collapse"][href="#searchDetail"]`）に変えた。id かデータ属性で特定すること
- **テストはデモ商品「彩のジェラートCUBE」の規格の並び順に依存している。** `入力_在庫アラート閾値(1, ...)` / `(7, ...)` が規格行の番号を決め打ちしており、`NO_FIXTURES=1` でデータも作り直さない。学習者が既存の規格（フレーバー・サイズ）に規格分類を足すと並び順がずれて落ちる。README のウォームアップに変更しないよう `[!CAUTION]` を置き、壊した場合の復旧手順（`docker compose down -v && up -d`）も書いた。**本来はテスト側を並び順非依存（規格分類名で行を特定する等）にすべきだが**、受け入れ基準そのものを書き換えるリスクを避け、今は注意喚起で対処している。テストを触る機会があれば直すこと

## DB エンジン・バージョン

**MySQL 8.4 を明示指定**する（`8.0` や `latest` は使わない）。

- EC-CUBE 4.3 の対応レンジは MySQL 8.0〜8.4
- 8.0 は Extended Support が 2026年4月に終了済みで、実質セキュリティパッチが出ない
- 8.4 は LTS で Extended Support 終了が約2032年4月。PostgreSQL 12〜16（EOL 2028年11月）より長く持つ
- EC-CUBE が MySQL 9.x 系に対応したら見直す

## Docker Compose 構成

EC-CUBE 公式は用途別の差分ファイルを `-f` で重ねる方式だが、学習者に分かりやすいよう **1本の `docker-compose.yaml` に統合**した。

- アプリは公式イメージ `ghcr.io/ec-cube/ec-cube-php:8.1-apache` を基にする（PHP バージョンを EC-CUBE 側に追従させるため。Xdebug 用の薄いレイヤーだけ重ねている。後述）
- nodejs サービスは置かない（フロントの Sass/JS ビルドが必要になったら検討）
- **named volume に分離しない。** 公式の `docker-compose.dev.yml` は `var` と `vendor` を named volume にしているが、それだとホスト側に実体が無く、IDE から依存ライブラリへ定義ジャンプできず、ログも直接開けない。Linux 前提でバインドマウントのオーバーヘッドが無いため分離をやめた（`mysql-data` のみ named volume）
  - 副作用としてホスト側に `vendor`（約190MB）と `var/cache` が置かれる。VS Code の inotify 上限に当たらないよう `.vscode/settings.json` に `files.watcherExclude` を入れている

**`USER_ID`/`GROUP_ID` を渡すこと（必須）**: 公式イメージの entrypoint は未インストール状態での初回起動時に、ドキュメントルート全体を `chown www-data` する。リポジトリのルートをそのままマウントしているため、対策なしだと `.git` を含むリポジトリ全体がコンテナ内 UID 所有になり、ホストから編集も git 操作もできなくなる。ホストの UID/GID を渡せば entrypoint が `usermod`/`groupmod` してから chown するので、実質「ホストユーザー所有に戻す」操作になる。README で学習者に `.env` へ `UID=$(id -u)` / `GID=$(id -g)` を書かせている。

**mysql の healthcheck には `start_period: 30s` が要る**: 初回起動時の MySQL 初期化は10〜15秒かかり、`start_period` 無しだと猶予（3秒×3回）を超えて unhealthy 判定になる。`depends_on: condition: service_healthy` の `ec-cube` は一度失敗すると起動されないため、学習者には原因不明のエラーに見える。必ず残すこと。

## `ECCUBE_AUTH_MAGIC` を学習者に生成させる

パスワードのハッシュ化に使う秘密の値。標準インストーラーは未設定なら自動生成するが、**セキュリティ基礎の学習として意図的に学習者自身に生成させる**。

- `.env.example` の `ECCUBE_AUTH_MAGIC=` を、`openssl rand -hex 32` 等で生成した値で埋めさせる
- `docker-compose.yaml` 側は `${ECCUBE_AUTH_MAGIC:?...}` とし、**値を設定しない限り `docker compose up` 自体が失敗する**ようにして、確実に自分で生成する体験をさせる
- **`.env.example` の値は空にしておくこと。** Compose の `:?` は「未設定または空」のときしか発動しない。以前は `ECCUBE_AUTH_MAGIC=<change.me>` というプレースホルダを置いていたが、これは非空の値なので `cp .env.example .env` した時点でチェックを素通りし、秘密値がプレースホルダのままインストールできてしまっていた。プレースホルダ文字列を置きたくなったら、この仕組みが死ぬことを思い出すこと

## 本体取り込み時の `.github` 対応

EC-CUBE 公式の `.github/workflows/` は**そのままコピーしてはいけない**。有効化した瞬間に外部サービス連携で失敗するか、本体のリリース/デプロイの仕組みに触れる恐れがある。本体を取り込み直すときは毎回:

1. `.github/workflows/` を全削除する（`coverage.yml`・`deploy.yml`・`e2e-test.yml`・`penetration-test.yml`・`vaddy*.yml`・`zaproxy.yml` などの workflow 一式と `actions/`・`vaddy/`）。残すのは `.github/.htaccess` のみ
2. `dependabot.yml`・`CONTRIBUTING.md`・`ISSUE_TEMPLATE*`・`PULL_REQUEST_TEMPLATE.md` も本体プロジェクト向けの内容なので削除し、課題用に作り直す（`PULL_REQUEST_TEMPLATE.md` は学習者から本体への PR を想定していないので作らない）
3. 課題用の `ci.yml` を置く。自前の `docker-compose.yaml` をそのまま CI でも起動し、`codecept run acceptance -g stock_alert` だけを実行する。`ENABLE_CI` リポジトリ変数によるオプトイン方式は本体から踏襲している

`dependabot.yml` は **GitHub Actions のみ**を対象にする。composer / npm / docker を対象にすると、バージョンを取り込み時点で固定する方針と衝突し、テンプレートをコピーした学習者のリポジトリにも大量の更新 PR が出てしまうため。本体側の脆弱性は Dependabot alerts で検知し、必要ならテンプレートを作り直す。

## 学習者に実装させる範囲

EC-CUBE 標準に「在庫アラート」機能が無いため、既存ファイルを空にして穴埋めさせる形式は採らず、**素の 4.3 に機能を新規追加させる**構成にした。変更対象は README の「実装内容」を正とする。`codeception/` 配下の E2E テストは変更不要（「テストが通ることが最低ライン」を明確にするため）。

- 「在庫僅少のみ」の絞り込みは `ProductClassRepository` ではなく、商品一覧が実際に使っている `ProductRepository::getQueryBuilderBySearchDataForAdmin()` に条件を足すのが既存コードの作法に合う

## リポジトリ配布方式

**GitHub Template Repository** を使う。Fork ではない理由は、アップデート反映が初学者には難しい／受講者同士のコードが見えてしまう／Template Copy ならクリーンな履歴で始められる、の3点。

- **バージョンは取り込み時点の最新安定版タグに固定する**（現在は `4.3.1-p1`）。固定の日付やタグ名を README / `AGENTS.md` に埋め込みすぎず、取り込み時に確認する運用とする
- **本体の git 履歴は持ち込まない。** 公式リポジトリは 216MB・10年以上の履歴があり、そのまま import すると教材が不必要に肥大化する。ソースツリーをクリーンな単一コミットとして取り込む
- **本体アップデートには追従しない。** ファイル数が桁違いで個別案内は非現実的だし、本体のリリース頻度も低い（4.3.0→4.3.1 で約1年）。取り込み時点に固定し、重大な脆弱性が出たときだけテンプレートを作り直す
- 本体ソース一式を含むため clone が重い。README に「初回の clone には数分かかる場合があります」と添えてある

## 参考ドキュメントのリンク方針

README の「参考ドキュメント（基礎から学びたい人へ）」について。

- **公式ドキュメントへのリンク集1章のみ**に留め、独自の解説やチュートリアルは書かない（作り込みすぎない方針のため）。各リンクに「この課題のどの場面で使うか」を1行添え、冒頭で「必須ではない」と明記する
- **リンク先はトップページではなく、学習の入り口になるページを指す。** トップページは目次でしかなく、初学者はどこから読めばよいか分からないため。サブリンクは本課題で実際に触るもの（Entity / Repository / FormType / テンプレート）に絞る
- **リンクのバージョンを固定する**（PHP 8.1 / Symfony 6.4 / Doctrine ORM 2.20 / Twig 3）。特に Doctrine ORM は公式の "stable" が 3.x を指しており、3.x ではアノテーション記法が廃止されているため、固定しないと動かない情報へ誘導してしまう。**本体のバージョンを上げるときは、このリンク群も composer.json に合わせて見直すこと**
- 動画は1本だけ併記している。古いバージョンが対象のものが多いのでその旨を必ず添える。差し替え・非公開のリスクがあるため増やさず、リンク切れに気づいたら削除する

## ウォームアップ課題

本課題に入る前に、管理画面・フロントの基本操作に慣れさせるセクション。「画面で操作 → 結果をレポートに記録」という型にして、本課題（実装 → 動作確認 → レポート化）と同じサイクルを先に体験させる狙い。

項目は本課題（ProductClass・商品規格）への直結度で選んだ。

1. **商品規格を作る** — 規格（ClassName）と規格分類（ClassCategory）の親子関係。本課題そのものが ProductClass の拡張なので最優先
2. **商品登録 → フロント表示** — Product / ProductClass とフロント表示の対応。カテゴリ紐付けはここに含め、独立項目にしない（本課題との直結度が低いため）
3. **在庫の増減 → フロント表示** — 「在庫0＝売り切れ表示」は本課題の「閾値以下でアラート表示」に直結する
4. **ブロック管理・レイアウト管理** — 画面が「レイアウト＋ブロック」でできていることの理解。Twig を編集する心理的ハードルを下げる狙い
5. **注文の一連の流れ** — 本課題との直結度は低いが、EC サイトを扱う以上「購入の流れ」は理解しておくべき、という判断で必須項目とした

README に書くときの注意: EC-CUBE の UI ラベルは ClassName が「規格名」、ClassCategory が「規格分類」（`messages.ja.yaml` の `admin.product.class_name` / `admin.product.class_category`）。「規格値」という語は EC-CUBE に存在しないので使わないこと。ClassCategory の管理は独立したナビ項目ではなく、「商品管理 > 規格管理」から各規格にドリルダウンする形。「商品管理 > カテゴリ管理」は商品カテゴリツリー用で ClassCategory とは無関係なので混同しないこと。在庫数の編集も独立した画面は無く、商品編集画面（規格なし商品）か商品規格編集画面（複数規格の商品）の中にある。

## デバッグ環境

**VS Code + Xdebug でのブレークポイントデバッグ**を用意している。カスタマイズ中にエラーが出たとき、学習者が自力で追えるようにするため。

- 公式イメージに Xdebug が同梱されていないため、`dockerbuild/Dockerfile` で公式イメージの上に `pecl install xdebug` を重ねている。「自前 Dockerfile ビルドはしない」という当初決定からの逸脱にあたるが、あの決定の趣旨は **PHP バージョンを EC-CUBE 側に合わせる**ことであってビルド禁止ではない、というユーザー判断で許容された。ベースイメージは変えていないので趣旨は保たれている
- `xdebug.mode` の既定は `off` とし、`.env` の `XDEBUG_MODE` で切り替えさせる。常時 debug にすると通常利用時のオーバーヘッドと `Could not connect to debugging client` ログが出るため
- Linux ネイティブの Docker Engine では `host.docker.internal` が既定で使えないので、`extra_hosts: ["host.docker.internal:host-gateway"]` が要る（Docker Desktop でも無害）
- Xdebug が繋がらないときの代替（`dump()`/`dd()`、`var/log/dev/` の日付別ログ、Symfony プロファイラツールバー、`ECCUBE_PHPINFO_ENABLED=1` での管理画面 phpinfo()）も README に併記している
- **ログは `docker compose exec ... tail -f var/log/dev/site-*.log` で案内しない。** `exec` はシェルを介さないためグロブがホスト側で展開され、しかもログは日付ごとにファイルが分かれるので `-f` が日付をまたいだ時点で何も流れてこなくなる（学習者が「ログが出ない」で詰まる）。`var/` を named volume に分離していない＝**ホストから直接読める**利点を活かし、エディタで当日分を開く案内にしている
- Copilot のインライン補完を `.vscode/settings.json` で無効化している。「答えを直接教えない」方針と、チャットベースの AI 利用を徹底するため。チャット欄での質問は制限していない旨を README に明記してある

**`.env` の扱い（ハマりどころ）**

- ルート直下の `.env` は **Docker Compose が `${VAR}` を展開するためだけ**に読まれる。`environment:` に明示的に書かない限りコンテナには注入されない。EC-CUBE 側で使う環境変数を増やすときは、`.env` に足すだけでなく `docker-compose.yaml` の `environment:` にも配線すること
- `.env` を書き換えても、実行中コンテナの環境変数はコンテナ作成時点で固定されている。`docker compose up -d`（再作成）が必要で、`restart` では反映されない
- EC-CUBE 自身の `.env` 読み込み（`index.php`・`bin/console`）は `if (!isset($_SERVER['APP_ENV']))` で囲われており、Compose が常に `APP_ENV` を渡すこの構成では走らない。Compose 側の変数展開用 `.env` とアプリ側の設定が二重に効く心配はない
- Apache 設定の `PassEnv` は4つしか列挙していないが、EC-CUBE は mod_php なので `environment:` の値はそのまま PHP から見える。`environment:` に変数を足すたびに `PassEnv` へ追記する必要はない

## オプション課題（クラウドデプロイ）を用意しない判断

独立したオプション課題としては**用意しない**。Render + Neon（無料 PostgreSQL の30日失効、単一 Dockerfile 制約、メモリ 512MB 制約）も無料レンタルサーバー（EC-CUBE の動作実績が無く、PHP バージョンや実行時間の制約を個別に検証する必要がある）も、課題化するには検証コストが見合わず、未検証のまま出すのはリスクが高いため。

代わりに README の「環境構築」章で、EC-CUBE のインストール方法には①クラウド版（新規受付停止中）と②ダウンロード版の2系統があり本課題は②を採っている、という位置づけを軽く紹介するに留める。zip 版をレンタルサーバーにデプロイしてみるのもおすすめ、という一言は添えるが、費用が発生するため必須にはしない。

## コピペ対策

「AI の出力をコピペするだけで、理解しないまま完了できてしまうのではないか」という懸念への対応。

**前提**: 入口は原理的に塞げない。`AGENTS.md` のヒント縛りも Copilot インライン補完の無効化も学習者のリポジトリ内にあるので削除できるし、README を丸ごと外部の AI に貼れば完成コードが得られる。そこで**出口（何をもって完了とするか）側**を変えた。狙いは「コピペを防ぐ」ことではなく、**「コピペしても理解が残る」「理解していないことが露見する」**設計にすること。

| 案 | 採否 |
| --- | --- |
| ① 動作確認の証跡を要求する | **採用** |
| ② `REPORT.md` の問いを、自分のコードを読まないと書けない形にする | **採用** |
| ③ 提出後に評価者の前で15分説明させる | 見送り。最も確実だが評価者の工数が要るため、運用側の判断に委ねる |
| ④ ウォークスルー中に小改造をその場で依頼する | 見送り。効果は最高だが「作り込みすぎない」方針と強く衝突する |

**① `REPORT.md`「動作確認の記録」の設計**

- 9ケースは `.claude/skills/review/SKILL.md`「境界値・エッジケース」の表で E2E 欄が `—` の項目から選んだ。テストが通っていても壊れうる箇所と一致する
- **期待する挙動を表に書かない。** 書くとそのまま記入欄に転記されてしまう。記入欄は「画面はどうなったか」という**観察の記録**にし、正解は README の「画面仕様」から自分で導かせる
- ケース6（規格なし商品のコンソールエラー）とケース9（`min` 属性を消してから負値を送信）は開発者ツールの操作が必須で、AI に代行させられない
- Xdebug のスクリーンショットは、**手を動かさないと成果物が作れない**のが強み。整備済みのデバッグ環境への投資も回収できる
- 「想定と違った箇所と、その対応」欄を設け、食い違いを見つけること自体を成果として扱う。本文で「直す前に記録してください」と促しているのは、直すと何が起きていたかが残らず、「直したくないから書かない」という動機も生まれるため

**② `REPORT.md`「設計判断の根拠」の設計**

- 4-1（入力値が DB に届くまでの経路）が最も強い。クラス名・メソッド名を挙げさせるので、コードを追わないと書けない
- 4-7 で既存レコードの値を実際に DB で確認させ、マイグレーション時にデータ移行を考える習慣づけと対応させている
- 4-2〜4-6 は `.claude/skills/review/SKILL.md`「レビュー観点」の項目と1対1で対応させた。学習者の自己説明と評価者の観点が揃うので突き合わせやすい
- 節の参照は番号ではなく**節名**で書くこと。節を挿入すると番号が繰り下がるため

**AI の振る舞い**: この対策は、AI が `REPORT.md` の問いに直接答えると**まるごと無効化される**。詳細は `AGENTS.md`「`REPORT.md` の記入を代筆しない」を参照。

**残っている限界**: 観察文も AI にもっともらしく生成させられる。完全な防止ではなく、**手を動かすほうが早い状況を作る**のが狙い。確実性を求めるなら ③ を運用に組み込むのが最も効く。`REPORT.md` の 4-1〜4-7 は、そのまま口頭質問の台本として使える粒度で書いてある。

## 商品規格編集画面の2つの実装方法をどこまで明かすか

README の「実装内容」の表の直後で、① Form クラスと Twig を直接編集する ／ ② `@FormAppend` によるエンティティ拡張、の2つを**明示している**。

伏せない理由: 対象が初心者で、「実装方法が複数あります」と書いても**2つ目の存在に気づけない**。`@FormAppend` は EC-CUBE 固有の仕組みで、知らなければ検索語すら思いつかない。結果として全員が①に流れ、狙いだった「2案を比較して選ぶ」という設計判断の練習が成立しない。伏せて守られるのは探索の手間だけで、学習価値ではなかった。

線引きは意図的なもの。変えるときは理由ごと更新すること。

| 明かす | 残す |
| --- | --- |
| 方法が2つあることと、それぞれの概要 | **どちらを選ぶか**（＝この項目の本体） |
| `@FormAppend` という名前、`DoctrineOrmExtension.php` の所在 | `@FormAppend` の**書き方**（`type` / `options` / `auto_render` に何を渡すか）。`FormAppend.php` を読ませる |
| `product_class.twig` に「エンティティ拡張の自動出力」ループがあること | ①で編集する **Form クラスがどれか** |
| 比較の観点（変更量・影響範囲・波及・拡張だと分かるか） | 観点ごとの評価と結論 |

- ①②の番号は、README・`AGENTS.md`「実装方法が複数ある項目の扱い」・`REPORT.md` の 4-2 の**3か所で揃っている必要がある**。片方だけ直さないこと
- 順序は「素直な方法（①）→ EC-CUBE 固有の仕組み（②）」。初心者が自力で思いつく方を先に置くと、②が「もう一つの選択肢」として読める
