# EC-CUBE 商品規格カスタマイズ課題

EC-CUBE 4.3 の商品規格（カラーバリエーション・サイズなど）に「在庫アラート」機能を追加する課題です。

## 前提条件

以下のツールをインストールしてください。

- Linux 環境 (WSL 含む)
- [Docker](https://nskint.sharepoint.com/sites/msteams_53d6da/SitePages/Docker.aspx)
- [git](https://nskint.backlog.jp/alias/wiki/977055)
- [VS Code](https://code.visualstudio.com/)
  - このプロジェクトを初めて開くと、推奨拡張機能のインストールを促されます。すべてインストールしてください。
- GitHub Copilot または Claude Code

> EC-CUBE はホスト側に PHP / Composer が無くても Docker だけで開発を進められます。`bin/console` などのコマンドは `docker compose exec ec-cube <コマンド>` の形で実行してください。

## 環境構築

### EC-CUBE のインストール方法について

EC-CUBE のインストール方法には、大きく分けて次の選択肢があります。

1. **EC-CUBEクラウド版** — EC-CUBE 社が提供するホスティング付きの SaaS 版。現在は新規受付を停止中で利用できません。
2. **ダウンロード版**
   1. **GitHub からのダウンロード**（本課題で採用） — ソースコード一式を取得し、自分で環境を構築する方法。無料で、Docker と組み合わせれば手元で完全にコントロールできる開発環境が作れます。今回はこの方法を前提に、リポジトリに Docker 環境を同梱しています。
   2. **zip 版のダウンロード** — レンタルサーバーへの配置を想定したパッケージ形式です。たとえば[さくらインターネットのクイックインストール](https://help.sakura.ad.jp/rs/2177/)のような機能を使うと、対応レンタルサーバー上に数クリックでセットアップできます。

今回は GitHub から落としたものを使用し、
本課題のリポジトリをコピーすれば動く状態にしています。

もし予算をかけられる場合は、余裕があるタイミングで zip 版を実際にレンタルサーバーへデプロイしてみるのもおすすめです（費用が発生するため必須課題にはしていません）。
ローカルの Docker 環境だけでは得られない、本番相当の環境に公開する体験ができます。

### 1. リポジトリのコピー

画面上部の **"Use this template"** ボタンから自分のアカウントにリポジトリを作成してください。
作成したリポジトリを `git clone` してローカルに落とします。

⚠️重要: Owner は自分、Visibility は Private ⚠️

### 2. 環境変数の設定

```bash
cp .env.example .env
```

`.env` を開き、`ECCUBE_AUTH_MAGIC` に安全なランダム文字列を設定してください。

```bash
openssl rand -hex 32
```

で生成した文字列を `ECCUBE_AUTH_MAGIC=` の後ろに設定します。**空のままだと `docker compose up` が起動時エラーで止まります。**

> **なぜ自分で生成するのか：** `ECCUBE_AUTH_MAGIC` はパスワードのハッシュ化に使われる秘密の値です。インストールごとに異なるランダム値にすることで、万が一データベースが漏洩しても、他のインストールと同じ手口でパスワードを解析されるリスクを下げられます。詳しくは `.env.example` のコメントを参照してください。

続けて、`.env` に自分の UID/GID を追記してください。

```bash
echo "UID=$(id -u)" >> .env
echo "GID=$(id -g)" >> .env
```

> **なぜ必要なのか：** コンテナは初回起動時にマウントしたディレクトリの所有者を書き換えます。UID/GID を渡さないと、このリポジトリ全体（`.git` を含む）がコンテナ内の固定ユーザー所有になり、ホスト側から編集や git 操作ができなくなってしまいます。

### 3. 環境チェック

起動する前に、必要なツールと設定が揃っているか確認します。`[FAIL]` が無ければ準備完了です（この時点ではまだコンテナを起動していないため、コンテナに関する `[WARN]` が出ますが問題ありません）。

```bash
bash scripts/check-env.sh
```

Claude Code または GitHub Copilot を使っている場合は `/check-env` を実行すると、問題があったときに AI が解決方法を案内します。

### 4. アプリケーションの起動

```bash
docker compose up -d
```

起動後、ブラウザで以下にアクセスできれば成功です。

- フロント: <http://localhost:8080/>
- 管理画面: <http://localhost:8080/admin/>（初期ログインID: `admin` / パスワード: `password`）
- mailcatcher: <http://localhost:1080/>

> 初回起動時は `composer install` やデータベースへの初期データ投入が自動で走るため、コンテナが完全に立ち上がるまで数分かかります。`docker compose logs -f ec-cube` で進捗を確認できます。

## デバッグ環境の準備（本課題の前に）

カスタマイズ中にエラーが出たとき、ログを読むだけでなく VS Code のブレークポイントで処理を止めて変数の中身を確認できると、原因調査がぐっと楽になります。この課題の Docker 環境には Xdebug を同梱しているので、以下の手順で有効化しておきましょう。

### 1. VS Code 拡張機能のインストール

このリポジトリを VS Code で開くと「PHP Debug」拡張機能のインストールを推奨されます（前提条件の章で触れた推奨拡張機能と同じ仕組みです）。インストールしてください。

### 2. Xdebug を有効にする

`.env` の `XDEBUG_MODE=off` を `XDEBUG_MODE=debug` に変更し、コンテナを再作成します。

```bash
docker compose up -d
```

> 常時 `debug` にしておくと動作が多少重くなります。デバッグが終わったら `off` に戻すことをおすすめします。

### 3. ブレークポイントで止めてみる

1. VS Code で確認したい PHP ファイルを開き、行番号の左をクリックしてブレークポイントを置く
2. 「実行とデバッグ」パネルで **Listen for Xdebug** を選択して開始する（緑の再生ボタン）
3. ブラウザで対象の画面（管理画面・フロントいずれも可）を開く
4. ブレークポイントの行が実行されると処理が一時停止し、変数の中身やコールスタックを確認できます

### うまく繋がらないとき

- `docker compose logs ec-cube` に `Xdebug: [Step Debug] Could not connect to debugging client` のようなログが出ていないか確認する
- VS Code側で「Listen for Xdebug」を開始し忘れていないか確認する
- ローカル環境のファイアウォールがポート `9003` への接続をブロックしていないか確認する

### ブレークポイントを使わない軽量な確認方法

簡単な確認であれば、こちらの方法も活用してください。

- `dump($var)` / `dd($var)` をコードに一時的に埋め込む（Symfony の VarDumper。`dd()` はその場で処理を止めて出力する）
- ログファイルを確認する — `var/log/dev/` に `site-2026-09-10.log` のような**日付ごと**のログが、ホスト側にそのまま置かれています。VS Code で**当日分**を開くのが手軽です。流れを追いたいときは `tail -F var/log/dev/site-$(date +%Y-%m-%d).log`（コンテナに入る必要はありません。`-f` ではなく `-F` にしておくと、その日のログがまだ無くてもファイルができるまで待ってくれます。日付が変わったら開き直してください）
- ブラウザ下部の Symfony プロファイラツールバー（`APP_ENV=dev` で有効）で、実行されたクエリやルーティング情報を確認する
- 管理画面の **設定 > システム設定 > システム情報** から `phpinfo()` を確認する（PHP 自体の設定値を調べたいとき用。`.env` の `ECCUBE_PHPINFO_ENABLED` が既定で `1` になっているため、そのまま開けます）

## EC-CUBE の基本操作に慣れる（本課題の前に）

いきなり「在庫アラート」機能のカスタマイズに入る前に、EC-CUBE の管理画面・フロント画面の基本操作に一通り触れておきましょう。ここで得る理解（特に商品規格まわり）は、この後の実装でそのまま役立ちます。

それぞれの項目を実際に操作し、気づいたことを `REPORT.md` の「0. ウォームアップ」に記入してください。
このセクションは課題の要件そのものではないので、AI に画面の場所や操作手順を直接聞いてもらって構いません。

また、課題実施の記録を `REPORT.md` に記述＆提出してもらうので、中身を確認しておいてください。

> [!CAUTION]
> **デモ商品「彩のジェラートCUBE」と、それが使っている規格「フレーバー」「サイズ」の構成は変えないでください。**
>
> E2E テストがこの商品の規格の並び順を決め打ちで参照しています。既存の規格に規格分類を追加・削除したり、この商品の規格構成を変更したりすると並び順がずれ、**実装が正しくてもテストが落ちます**。ウォームアップでは新しい規格を作り、新しい商品を登録して試してください（既存の規格を**使う**のは問題ありません。定義を**変える**のが問題です）。
>
> うっかり変更してしまった場合は、データベースを作り直せば元のデモデータに戻せます。
>
> ```bash
> docker compose down -v   # -v を付けて、データベースのボリュームごと削除します
> docker compose up -d
> ```
>
> `-v` が無いとボリュームが残り、データベースは元のままなので注意してください。
>
> 消えるのはデータベースの中身（登録した商品・規格・注文・設定など）だけで、**書いたコードは消えません**。作り直しの際にデモデータの投入とキャッシュのクリアが自動で走るため、起動まで数分かかります。

### 1. 商品規格を作ってみる

管理画面: **商品管理 > 規格管理**

- 新しい規格（例:「素材」）を1つ作成する
- その規格に、規格分類（例:「綿」「ポリエステル」）を2〜3個追加する

規格（サイズ・色など）と規格分類（S/M/L、赤/青など）は親子関係になっています。この後の商品登録で、これらを組み合わせて商品バリエーションを作ります。

### 2. 商品を登録してフロントで確認する

管理画面: **商品管理 > 商品登録**

1. 画像を1枚アップロードする
2. 適当なカテゴリを商品に紐付ける
3. 公開状態を「公開」にする
4. 一旦登録する（先に登録しないと規格を設定できません）
5. 上で作った規格（または既存のデモ用規格）を使い、複数の規格を持つ商品にする
6. 規格を設定する前と後で、商品登録画面がどう変わるか確認する

登録後、フロント（<http://localhost:8080/>）でトップページ → カテゴリ → 商品詳細まで辿り、登録した内容がどう表示されるか確認してください。商品詳細画面の規格選択（プルダウン）にも注目しましょう。

### 3. 在庫を操作してフロント表示の変化を見る

管理画面: 登録した商品の編集画面（複数規格がある場合は商品規格編集画面）

- いずれかの規格の在庫数を `0` にする
- フロントの商品詳細画面でその規格を選択し、表示（カートボタン・在庫表示など）がどう変わるか確認する

ここで見た「在庫0＝売り切れ表示」の仕組みが、これから実装する「在庫アラート（閾値以下で警告表示）」の土台になります。

### 4. ページのレイアウト・ブロックを編集する

管理画面: **コンテンツ管理 > ブロック管理** / **コンテンツ管理 > レイアウト管理**

- フリーエリアのブロックを1つ新規作成し、任意のテキストを入れる
- レイアウト管理でトップページを開き、作成したブロックを配置する

フロントのトップページで反映されているか確認してください。EC-CUBE の画面は「レイアウト」と「ブロック」の組み合わせで構成されており、この仕組みは他の画面にも共通しています。

### 5. 注文の一連の流れを体験する

この課題とは関連性ありませんが、フロントでの注文から管理画面での確認までの一連の流れも体験してみてください。

- フロントで会員登録し、登録した商品をカートに入れて注文する
- mailcatcher <http://localhost:1080/> で送信されたメールの確認
- 管理画面: **受注管理 > 受注一覧** で、その注文が登録されていることを確認する

このようにいろいろな機能に触れ、
EC-CUBE における「商品」「会員」「注文」の関係を掴んでおくと、今後別の機能を追加する際の理解が早まります。

## 課題内容

この課題では以下の4つを学びます。

- **EC-CUBE の商品モデル** — 商品（Product）と商品規格（ProductClass）の関係を理解し、規格ごとのデータを扱う
- **Doctrine ORM** — エンティティへのカラム追加とマイグレーションによるスキーマ反映、Repository でのクエリメソッド追加
- **入力値の検証** — 不正な値を保存させないためのバリデーションを、どこにどう書くか
- **EC-CUBE のカスタマイズ作法** — 管理画面（Symfony Controller / Form / Twig）とフロント画面それぞれの拡張方法

### 画面仕様

#### 管理画面：商品規格編集画面

- 商品規格の編集行に「在庫アラート閾値」の入力欄を表示する
  - 未入力（null）の場合はアラート機能を使わない
  - ラベルは **`在庫アラート閾値`** とすること
  - フォーム項目名は **`stock_alert_threshold`** とすること（E2E テストは、この名前から生成される入力欄の id `product_class_matrix_product_classes_{n}_stock_alert_threshold` を参照します）
- 保存すると、閾値が商品規格に保存される
- **0 未満の値は保存できないようにする**
  - 負の数を入力して保存しようとした場合は、エラーを表示して保存しないこと
  - ブラウザの入力制限（`min` 属性など）だけで済ませないこと。開発者ツールで HTML を書き換えれば簡単に回避できてしまうため、**サーバー側でも必ず検証する**
  - 検証ルールをどこに書くか（エンティティか、フォームか）も考えてみてください

#### 管理画面：商品一覧画面

- 検索フォームに「在庫僅少のみ」の絞り込みチェックボックスを表示する
  - ラベルは **`在庫僅少のみ`** とすること
  - 検索フォームの項目名は **`stock_alert_only`** とすること（E2E テストは、この名前から生成される入力欄の id `admin_search_product_stock_alert_only` を参照します）
  - チェックすると、在庫数が閾値以下（かつ閾値が設定されている）規格を持つ商品のみを一覧に表示する

#### フロント：商品詳細画面

- 表示中の規格の在庫数が閾値以下の場合、「残りわずか」のバッジを表示する
  - バッジには **`stock-alert`** クラスを付与すること
- 規格（色・サイズ等）を切り替えたときも表示が追従すること

> **ヒント：** EC-CUBE のフロント商品詳細画面は、規格選択時に JavaScript（`eccube.checkStock` 等）で在庫を動的に確認しています。この仕組みをどう拡張するか調べてみてください。

| 管理画面：商品規格編集画面                                                               | 規格ごとに閾値を入力・保存できるようにする。この画面は通常の商品編集画面とは別物（`admin_product_product_class` ルート）です。**この項目だけは実装方法が2通りあります**（表のあとの補足を参照）                                                     |
| `src/Eccube/Form/Type/Admin/SearchProductType.php`                                       | 商品一覧の検索フォームに「在庫僅少のみ」の絞り込み項目を追加する                                                                                                                                            |
| `src/Eccube/Repository/ProductRepository.php`（`getQueryBuilderBySearchDataForAdmin()`） | 「在庫僅少のみ」で商品を絞り込むクエリ条件を追加する                                                                                                                                                        |
| `src/Eccube/Resource/template/admin/Product/index.twig`                                  | 商品一覧画面に「在庫僅少のみ」のチェックボックスを表示する                                                                                                                                                  |
| `src/Eccube/Twig/Extension/EccubeExtension.php`（`getClassCategoriesAsJson()`）          | 規格ごとの JSON に、閾値以下かどうかの判定結果を追加する                                                                                                                                                |
| `src/Eccube/Resource/template/default/Product/detail.twig`                               | 「残りわずか」バッジ（`stock-alert` クラス）を表示できるようにする。なお、JSON を JS 変数に埋め込む行（`eccube.classCategories`）は既に存在するので追加は不要                                                                                                                                              |
| `html/template/default/assets/js/eccube.js`（`checkStock()`）                            | 規格切り替え時に「残りわずか」バッジの表示・非表示を切り替える                                                                                                                                              |

参考: [EC-CUBE 4 開発者向けドキュメント](https://doc4.ec-cube.net/)

> [!IMPORTANT]
> **マイグレーションファイルは自分で書いてください。** EC-CUBE は基本的にスキーマの源泉を Entity の属性としており、単純なカラム追加であれば `bin/console doctrine:schema:update --force` だけでも反映できます。ただし実務では、カラムを1つ追加するだけでも「既存データにどんな値を入れるか」「デフォルト値は必要か」といった検討が必要になることが多く、それを都度きちんと考える習慣をつけるため、本課題では**あえてマイグレーションを書く**方針にしています。
>
> `bin/console doctrine:migrations:generate` で雛形を生成し、`up()`/`down()` に ALTER 文を手で書いて `doctrine:migrations:migrate` で反映してください。**`doctrine:migrations:diff` は使わないでください。** 単純なカラム追加でも差分をそのまま出力してしまい、上記の「考える」ステップが省略されてしまいます。

なお、初めて `doctrine:migrations:migrate` を実行すると、EC-CUBE 本体に同梱されている過去のマイグレーションも一緒に実行され、`... was executed but did not result in any SQL statements` という警告が何件も表示されます。これは既にスキーマへ反映済みの内容を再確認しているだけで、エラーではありません。無視して問題ありません。

> [!TIP]
> **商品規格編集画面に入力欄を追加する方法は、大きく2通りあります。** 自力では気づきにくいところなので、先に示しておきます。
>
> - **① Form クラスと Twig を直接編集する** — 商品規格編集画面が使っている Form クラスに項目を追加し、`src/Eccube/Resource/template/admin/Product/product_class.twig` の表にも列を追加する方法です。やっていることが目で追いやすい反面、変更するファイルは増えます。なお、どの Form クラスがこの画面を担当しているかは自分で調べてみてください
> - **② EC-CUBE の「エンティティ拡張」の仕組みを使う** — エンティティのプロパティに `@FormAppend` というアノテーションを付けると、対応するフォーム項目が自動的に組み立てられます（仕組みは `src/Eccube/Form/Extension/DoctrineOrmExtension.php` にあります）。`product_class.twig` にも「エンティティ拡張の自動出力」というループが最初から用意されています
>
> **どちらでも要件は満たせます。どちらを選ぶかは自分で決めてください。** 判断がつかないときは、AI に「①と②を比較してほしい」と聞いてみましょう。変更するファイルの数、既存コードへの影響、他の画面への波及、「これは拡張である」と後から読んで分かるか、といった観点で比べられます。
>
> **選んだ理由は `REPORT.md` の「4-2」に書いてください。** どちらを選んだかではなく、理由を説明できることが大事です。

`codeception/` 配下の E2E テスト（`StockAlertAdminCest.php` / `StockAlertFrontCest.php`）は変更不要です。
ここに書かれた E2E テストがすべて通ることが最低ラインです（実行方法は後述します）。
ただしテストが見ているのは主要な動作だけなので、**通ったあとに自分の目で動作確認するところまで**が課題です。

### 進め方の目安

初めて EC-CUBE のコードに触れる場合は、以下の順番で進めると迷いにくいです。1つ進めるたびに、管理画面・フロントを実際に開いて動作確認しながら進めましょう。

1. **エンティティにフィールドを追加する** — `ProductClass` に閾値のフィールドを追加する
2. **マイグレーションを作成して DB に反映する** — 追加したカラムがテーブルに存在するか、DB を直接確認してみましょう
3. **管理画面：閾値を保存できるようにする** — 保存後、DB に正しく反映されているか確認する。負の値を入力するとエラーになることも確認する
4. **管理画面：「在庫僅少のみ」で絞り込めるようにする**
5. **フロント：「残りわずか」を表示できるようにする** — 規格を切り替えても表示が追従するか確認する
6. **E2E テストを実行し、すべて通ることを確認する** — コマンドは[「E2E テストの実行」](#e2e-テストの実行)を参照
7. **自分の目で動作確認する** — `REPORT.md` の「動作確認の記録」に沿って、テストが見ていないケースを画面で確認する

一度に全部作ろうとせず、1ステップ進めるごとに「実装 → 動かして確認 → 次へ」を繰り返すのがおすすめです。

## 何をすればいいかわからなくなったときは

「次に何をすればいいか分からない」「どこから手を付ければいいか分からない」——
そんなときは一人で悩まず、AI に頼ってください。AI は答えをそのまま教える設定にはなっていませんが、
**今の状況を整理して、次の一歩を示してくれる** 心強い相棒です。

ここでは「こう頼ればいいよ」という具体例を紹介します。

### 頼り方の例

#### 🧭 そもそも何から始めればいいか分からないとき

README.md をチャットに添付（または開いた状態）にして、こう聞いてみてください。

> 「README.md を読みました。何から始めればいいですか？最初の1ステップを教えてください」

AI が課題内容を踏まえて、たとえば「まず `src/Eccube/Entity/ProductClass.php` にフィールドを追加するところから始めましょう」のように案内してくれます。

#### 🪜 今やっていることが終わって、次に進みたいとき

実装したファイルを開いた状態で、こう聞いてみてください。

> 「`ProductClass.php` にフィールドを追加しました。次は何に取り組むのがよさそうですか？」

順番に迷ったときも、課題の流れに沿って次のタスクを提案してくれます。

#### 🌀 自分が今どこにいるか分からなくなったとき

> 「いま実装したコードを見て、課題のどこまで進んでいるか整理してもらえますか？」

書いたコードと README.md の要件を突き合わせて、進捗と残タスクを整理してくれます。

#### 🤔 やることは分かるけど、書き方が分からないとき

> 「商品規格編集画面に閾値の入力欄を追加したいのですが、どこから手を付ければいいか考え方を教えてください」

設計の方針や考えるべき観点を示してくれるので、それを元に自分で実装してみましょう。

#### 🚧 エラーが出て止まってしまったとき

ターミナルのログをそのまま貼り付けて、こう聞いてみてください。

> 「`docker compose up -d` を実行したら以下のエラーが出ました。原因の調べ方を教えてください。
> ```
> （ここにエラーログを貼る）
> ```」

エラーの読み方や、確認すべき場所を教えてくれます。

#### 🔍 自分のコードに自信がないとき

> 「いま書いた `EccubeExtension` の変更をレビューしてください」

実装した内容を見て、改善点やヒントを返してくれます（後述の「AI 自己レビュー」で使う `/review` も同じ仕組みです）。

### 頼るときのコツ

- **遠慮しない** — 「こんな初歩的なこと聞いていいかな」と思うことほど聞いてOKです。
- **状況を一緒に伝える** — 「何をしようとして」「どこで詰まったか」を添えると、的確な助言が返ってきます。
- **コードやログをそのまま貼る** — エラーメッセージやファイルの中身を見せると、推測ではなく事実に基づいて答えてくれます。
- **対話を重ねる** — 一度の質問で解決しなくても、返ってきた内容にさらに質問を重ねていくと理解が深まります。

### AI に聞く前に試すと良いこと

ちょっとしたことなら、自分で確認するほうが早い場合もあります。

1. **ログを読む** — `docker compose logs -f ec-cube` や、ブラウザの開発者ツールのコンソールを確認します。
2. **直前の変更を `git diff` で見直す** — 動いていた状態から何を変えたか確認します。
3. **README.md を読み返す** — 課題の要件や画面仕様が書いてあります。

それでも分からなければ、迷わず AI に頼りましょう。

## E2E テストの実行

実装が完了したらテストを実行して確認してください。

```bash
docker compose exec -e NO_FIXTURES=1 -e APP_ENV=test ec-cube \
  vendor/bin/codecept run acceptance -g stock_alert --env chrome-headless
```

エラーが出た場合は、テスト失敗時に出力される `codeception/_output/` 配下のスクリーンショット・HTML も確認してみてください。

> [!IMPORTANT]
> **E2E テストが通っても、実装が完成したとは限りません。**
>
> テストが検証しているのは主要な動作だけです。閾値が未設定のとき、在庫数無制限の規格、規格を持たない商品といったケースは検証していません。テストが通る状態でも、これらが壊れていることは珍しくありません。
>
> テストが通ったら、`REPORT.md` の「動作確認の記録」に沿って、**実際に画面を操作して自分の目で確認**してください。想定と違う動きを見つけたら、直すところまでが課題です。

## AI 自己レビュー

テストが通ったら、Copilot / Claude を使って自己レビューを行ってください。

```txt
/review
```

このリポジトリにあらかじめ設定されたレビュー観点（要件チェック・設計・コードの3観点）に基づいて、フィードバックが返ってきます。

## 提出方法

1. GitHub Actions を有効化する（初回のみ。**プッシュより先に済ませてください**）
   1. リポジトリの **Settings > Secrets and variables > Actions > Variables** タブを開く
   2. **New repository variable** をクリックする
   3. 名前を `ENABLE_CI`、値を `true` にして **Add variable** を押す
2. 実装した内容を自分の GitHub リポジトリの `main` ブランチにコミット・プッシュする
3. `main` にプッシュすると E2E テストが自動で実行される
4. ✅ が付いたら OK
   - 先にプッシュしてしまい CI が動かなかった場合は、**Actions** タブで `CI` ワークフローを選び、**Run workflow** から手動で実行できます
5. `REPORT.md` を記入し `main` にコミット・プッシュ
   - 「CI 実行結果」は URL ではなく、スクリーンショットかログを貼り付けてください
   - 「動作確認の記録」は、実際に画面を操作しながら記入してください。ブレークポイントのスクリーンショットも忘れずに
   - 「設計判断の根拠」は、自分が書いたコードを実際に開いて確かめてから記入してください
6. リポジトリに評価者を追加して参照権限を与え、リポジトリの URL を共有する

> [!WARNING]
> **GitHub Actions の利用料について**
>
> プライベートリポジトリでは GitHub Actions の実行時間が無料枠（2,000 分/月）に含まれます。
> Docker イメージのダウンロードや `composer install` があるため 1 回の CI に数分かかります。
> `main` への不要なプッシュを避け、ローカルで E2E テストを通してから push してください。
