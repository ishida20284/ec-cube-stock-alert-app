## 課題の要件

学習者向けの正の仕様は README.md の「画面仕様」。ここには、レビューや受け入れ判定に使う詳細（E2E テストが依存する識別子・境界値・エッジケース）を補足する。

機械的に合否が決まるのは E2E テスト（`codeception/acceptance/StockAlertAdminCest.php` / `StockAlertFrontCest.php`）が検証する範囲のみで、それ以外は `/review` やレビュー時に確認する観点として扱う（下表の「E2E」欄を参照）。

### 管理画面

| 画面 | 期待する動作 | E2E |
| --- | --- | --- |
| 商品規格編集画面（`admin_product_product_class`。通常の商品編集画面とは別画面） | 商品規格ごとに在庫アラート閾値を入力・保存でき、画面を開き直しても値が残る（＝DB に保存されている） | ✅ |
| 商品規格編集画面 | 0 未満の値を保存しようとするとエラーになり、保存されない。**サーバー側で検証していること**（`min` 属性等のクライアント側の制限だけでは要件を満たさない） | ✅※ |
| 商品一覧画面 | 検索フォームの「在庫僅少のみ」にチェックすると、在庫が閾値以下の規格を持つ商品だけが表示される | ✅ |

### フロント

| 画面 | 期待する動作 | E2E |
| --- | --- | --- |
| 商品詳細画面 | 選択中の規格の在庫が閾値以下のとき「残りわずか」を表示する | ✅ |

### E2E テストが依存している識別子

テストは以下の名前を直接参照しているため、これと異なる名前で実装するとテストだけが落ちる。学習者が「実装できているのにテストが通らない」と質問してきたときは、まずここを疑う。

| 箇所 | 識別子 | 参照している Page Object |
| --- | --- | --- |
| `ProductClass` のフィールド名 | `stock_alert_threshold`（フォーム項目の id が `product_class_matrix_product_classes_{n}_stock_alert_threshold` になる） | `Page/Admin/ProductClassEditPage::入力_在庫アラート閾値()` |
| 商品検索フォームの項目名 | `stock_alert_only`（id `admin_search_product_stock_alert_only`） | `Page/Admin/ProductManagePage::$検索条件_在庫僅少のみ` |
| 「残りわずか」バッジ | CSS クラス `stock-alert`、テキストに `残りわずか` を含む | `Page/Front/ProductDetailPage::在庫アラート表示確認()` |

これらはいずれも README.md の「実装内容」「画面仕様」で学習者に明示している。

**※ バリデーションのテスト（`在庫アラート閾値に負の値は保存できない`）について**

- クライアント側の制限を回避してから送信する必要があるため、`ProductClassEditPage::クライアント側入力制限を解除()` で、`executeJS` により全フォームに `novalidate` を付与し、閾値入力欄の `min` 属性を削除している。これをしないと、`min="0"` を付けた実装ではブラウザのネイティブ検証で送信自体がブロックされ、サーバー側の検証有無を判定できない
- 送信前に `document.body` へ目印の属性を付け、送信後に `waitForJS` でそれが消えている（＝ページが再読み込みされた）ことを確認している。これが無いと、**クライアント側の制限の解除に失敗して送信自体がブロックされた場合でも「保存されない」ためテストが通ってしまう**（検証が空振りする）
- 検証しているのは「**保存されないこと**」（保存完了メッセージが出ない／画面を開き直しても元の値のまま）のみ。エラーメッセージの文言や表示位置は、使う制約（`GreaterThanOrEqual` / `PositiveOrZero` / `Range` 等）によって変わるため、テストでは断定しない。**「エラーが表示されるか」はレビュー観点で確認する**

### 境界値・エッジケース

| ケース | 期待する挙動 | E2E |
| --- | --- | --- |
| 閾値が未設定（null） | アラート対象外。バッジを表示せず、「在庫僅少のみ」でもヒットさせない | — |
| 在庫数 == 閾値 | 「閾値以下」なのでアラート対象（`<=` で判定する） | — |
| 閾値 0 | 保存は許容する（0 以上の整数）。在庫 0 は下記の通り品切れ扱いのため、実質バッジは出ない | — |
| 負の閾値 | **保存を許容しない**（0 以上の整数のみ）。エラーを表示し、DB には保存しない。HTML の `min` 属性だけの制限は、開発者ツールで回避できるため要件を満たさないものとして扱う | ✅※ |
| 在庫 0（`ProductClass.stock_find` が false） | EC-CUBE 標準の品切れ表示（カートボタン無効化・「ただいま品切れ中です」）が優先されるべきで、「残りわずか」との併記は不自然。ただし README では触れていないため、どちらの実装でもテストは通る。レビューでは「考慮した形跡があるか」を見る程度に留める | — |
| 在庫数無制限（`stock_unlimited` = true） | 在庫数と比較できないためアラート対象外 | — |
| 規格なし商品（ClassCategory を持たない商品） | フロント詳細に規格の `<select>` が無く `checkStock()` が呼ばれないため、JS 側だけの実装ではバッジが出ない。バッジ表示は必須要件としないが、**JS エラーになったり既存の表示が壊れたりしないこと** | — |
| 規格が未選択（「選択してください」のまま） | バッジは非表示 | — |
| 非表示の規格（`ProductClass.visible` / `ClassCategory.visible` が false） | 既存の `getClassCategoriesAsJson()` と同様、JSON から除外されたままでよい | — |
| 1商品に該当する規格が複数ある場合の商品一覧 | 同じ商品が重複して並ばないこと（`getQueryBuilderBySearchDataForAdmin()` は `ProductClasses` を inner join している） | — |

## レビュー観点

以下の観点でレビューしてください。判断に迷う境界値は上記「課題の要件」の表を基準にすること。

### 1. 要件チェック

- 管理画面・フロント双方の仕様がすべて実装されているか
- 閾値が未設定（null）のときにアラート機能が働かないことを考慮しているか
- 在庫アラート閾値に 0 未満を弾くバリデーションが入っているか。**サーバー側で検証しているか**（`attr` の `min` 属性だけになっていないか）
- 在庫数無制限（`stock_unlimited`）の規格をアラート判定から除外しているか
- 在庫数と閾値の比較が「以下」（`<=`）になっているか
- 「在庫僅少のみ」の絞り込みで同じ商品が重複表示されないか
- マイグレーションファイルが `app/DoctrineMigrations/` に追加され、`up()` と `down()` の両方が書かれているか（`doctrine:migrations:diff` の出力をそのまま貼り付けたものになっていないか）

### 2. 設計観点

- Doctrine エンティティ・Repository・Controller・Form・Twig の役割分担が守られているか
- ビジネスロジック（閾値判定など）が Controller や Twig に漏れていないか
- 閾値判定が `ProductClass` 側のメソッドなどに集約されているか（Twig の `{% if %}` や JS に判定式が散らばっていないか）
- バリデーションが Symfony の仕組み（エンティティの `@Assert\...` 制約、またはフォームの `constraints` オプション）で表現されているか。Controller やリポジトリでの手書きの `if` チェックになっていないか
- 「在庫僅少のみ」の絞り込みが Repository の QueryBuilder で行われているか（全件取得して PHP 側でフィルタしていないか）
- フロントの規格追従が既存の `getClassCategoriesAsJson()` / `checkStock()` の拡張で実現されているか（不要な Ajax エンドポイントを新設していないか）
- 変更範囲が README「実装内容」で挙げたファイル周辺に収まっているか（EC-CUBE 本体の無関係なコアファイルを書き換えていないか）

### 3. コードレビュー

- クラス・メソッド・変数の命名が意図を正確に表しているか
- Twig テンプレートで XSS リスクのある出力方法を使っていないか（`|raw` の使用が既存の `class_categories_as_json` の範囲を超えていないか）
- 不要な null チェックや冗長なコードがないか
- 画面に出す文言をテンプレートへ直書きせず、`trans` と `messages.ja.yaml` を使う既存の作法に合わせているか
- 商品一覧の絞り込みで N+1 クエリが発生していないか
- 規格未選択・規格なし商品など、規格データが取得できないケースで JS が壊れないか
